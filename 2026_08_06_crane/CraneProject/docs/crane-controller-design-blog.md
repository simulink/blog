# Designing the pump-and-catch controller for `crane_sm`

This report explains how the controller in this project was designed, what each script contributes,
and how the controller ended up in the Simulink model.

## The problem

The model in this project recreates a gantry crane maneuver: move a trolley
with a suspended payload, swing the payload high enough to clear a wall, then
catch the load on the far side.

That is not a great fit for one linear controller from start to finish. At the
beginning, the controller must add energy to the pendulum. Near the end, the
controller must remove energy and settle the trolley. In the middle, it must
make a timed decision to push the trolley across the wall once the payload has
enough clearance.

The final design is therefore a hybrid controller:

1. Pump the pendulum to build swing energy.
2. Transfer the trolley once the payload is high enough.
3. Hold the trolley after the payload clears the wall.
4. Switch to an LQR catch controller when the swing is small enough.

In the current model, this logic lives in the `Control` subsystem of
`models/crane_sm.slx`. The plant lives in the `Plant` subsystem and returns the
measured signals needed by the controller:

- `xTrolley`
- `vTrolley`
- `xBob`
- `yBob`
- `theta`
- `omega`

The model logs these signals using signal logging, and the baseline regression
test reads them from `logsout`.

## Start with the simplest useful plant model

The Simscape Multibody model is the truth model for the demo. It includes the
trolley, pendulum, payload, wall geometry, and contact sensing. That is the
right model for visualization and final validation.

For controller design, the project also uses a smaller analytical model. This
model is in `scripts/tunePumpManeuver.m` and uses the standard nonlinear
cart-pendulum equations with state

```text
x = [xTrolley; vTrolley; theta; omega]
```

The analytical model is not a replacement for Simscape Multibody. It is a
fast sandbox for answering controller-design questions:

- What pendulum frequency should the pump command use?
- How long should the pump phase last?
- What force amplitude and phase avoid the wall?
- Can the final catch controller settle the system from the resulting state?

The physical parameters all come from `data/craneParameters.m`. The important
ones for the controller are:

```text
trolley mass       8.0 kg
payload mass       1.5 kg
pendulum length    1.4 m
gravity            9.81 m/s^2
force limit        60 N
wall X location    1.45 m
target X location  3.0 m
```

Using one parameter source matters. The analytical tuning model, generated
controller data, and Simscape model all read from the same function, so the
controller is not tuned against one set of numbers and simulated against
another.

## The pump phase

The first part of the maneuver deliberately excites the pendulum. The code
starts with the small-angle natural frequency:

```matlab
omega0 = sqrt(p.gravity / p.pendulumLength);
freq = p.pumpFrequencyScale * omega0;
```

The force command is a sinusoid at roughly that frequency, multiplied by a
smooth envelope:

```matlab
envelope = sin(pi * t / pumpDuration)^2;
u = amp * envelope * sin(freq * t + phase);
```

The envelope avoids an abrupt force at the start and end of the pump phase.
That is a small detail, but it makes the command easier to simulate and easier
to reason about.

The tuning script does not solve a large optimization problem. It performs a
small grid search over amplitude, duration, and phase:

```matlab
ampGrid = linspace(0.55, 1.0, 5) * p.pumpAmplitude;
durGrid = p.pumpDuration + linspace(-0.6, 0.6, 5);
phaseGrid = linspace(-pi/5, pi/5, 5);
```

For each candidate, it simulates the analytical cart-pendulum model, computes
payload clearance over the wall, checks final error, and scores the result.
That is enough for this project because the goal is not a globally optimal
crane trajectory. The goal is a clear, reproducible demo maneuver.

The model implementation uses the tuned pump constants generated by
`scripts/setupCraneController.m`:

```text
pump amplitude  37.2 N
pump duration   7.6 s
pump frequency  2.54122 rad/s
pump phase      pi/5 rad
```

During this phase, the MATLAB Function block also adds a centering term:

```matlab
centerForce = -ctrl_centerGain * xTrolley ...
              -ctrl_centerDamping * vTrolley;
```

That keeps the trolley from drifting too far while the payload is being pumped.

## Deciding when to transfer

The model uses Stateflow for the supervisory logic because the controller has
discrete operating modes and guarded transitions. In the current model, the
`Mode Logic` chart has four states:

```text
Pump -> Transfer -> PostClear -> LQRCatch
```

The important transition is from `Pump` to `Transfer`. It waits until the
payload is high enough, still on the near side of the wall, and moving in the
right direction:

```text
t > 1
yBob > wallTop + transferClearance
xBob < wallX
payload horizontal velocity > 0
```

The payload horizontal velocity is estimated from the measured trolley velocity
and pendulum angular velocity:

```matlab
vTrolley + L*cos(thetaWrapped)*omega
```

This is a useful example of putting a little physics into the mode logic. The
controller does not switch just because the payload is high. It switches when
the payload is high and moving toward the far side.

## Transfer and post-clear behavior

Once the payload is high enough, the controller applies a transfer force:

```matlab
force = ctrl_transferForce - ctrl_transferDamping * vTrolley;
```

This pushes the trolley across the wall while damping trolley velocity. After
the payload crosses past the wall, the mode changes to `PostClear`.

`PostClear` still protects against a low payload near the obstacle. If the
payload is not safely past the wall, the controller continues the transfer
push. Otherwise it becomes a simple trolley hold controller around the final
target:

```matlab
force = -ctrl_postClearGain * (xTrolley - ctrl_targetX) ...
        -ctrl_postClearDamping * vTrolley;
```

This intermediate mode keeps the LQR catch controller from being asked to do
too much while the payload is still in a large swing.

## The catch controller

The final controller is an LQR designed from a small-angle linear model. The
design script is `scripts/designLQRCatchController.m`.

The state is:

```text
[x; xdot; theta; thetaDot]
```

where `theta` is measured from vertical. The linearized matrices are:

```matlab
A = [0 1 0 0; ...
     0 0 -(m*g)/M 0; ...
     0 0 0 1; ...
     0 0 ((M+m)*g)/(M*L) 0];

B = [0; 1/M; 0; -1/(M*L)];
```

The weighting matrices come from `craneParameters.m`:

```matlab
p.lqrQ = diag([25 4 90 8]);
p.lqrR = 0.25;
```

The large angle weight says that the catch controller should care strongly
about pendulum angle. The velocity and trolley-position weights keep the
settling behavior reasonable without demanding excessive force.

The generated gain in `data/craneControllerData.mat` is:

```text
ctrl_K = [-10  -21.524  -312.58  -112.3]
```

The in-model force law uses a scaled version of that gain:

```matlab
x = [xTrolley - ctrl_targetX; vTrolley; thetaWrapped; omega];
force = ctrl_lqrScale * ctrl_K * x;
```

with:

```text
ctrl_lqrScale = 0.12
```

That scale factor is a pragmatic demo choice. The full LQR gain is aggressive
for the nonlinear, saturated, wall-clearance maneuver. Scaling it keeps the
catch behavior within the same 60 N actuator limit used by the rest of the
demo.

## Saturation is part of the design

The model has two layers of force limiting:

- The MATLAB Function block clamps the command to `+/- ctrl_forceMax`.
- The Simulink `Force Saturation` block clamps the output again.

For production code, duplicate saturation usually deserves a design review. In
this demo, it is useful because the controller code remains self-contained and
the diagram still shows the actuator limit explicitly.

The final force command is converted to a physical signal and applied to the
Simscape Multibody prismatic joint.

```text
Control/forceCmd -> Plant/Force Converter -> Trolley Prismatic Joint
```

## How the controller gets into the model

`scripts/setupCraneController.m` is the bridge between design scripts and the
Simulink model. It:

1. Loads the project parameters.
2. Calls `designLQRCatchController`.
3. Computes derived values such as wall top, pump frequency, and force limits.
4. Saves `ctrl_*` variables to `data/craneControllerData.mat`.
5. Assigns the same variables into the MATLAB base workspace for simulation.

The generated model script, `scripts/buildCraneSimscapeModel.m`, shows how the
controller was originally constructed:

- A Stateflow chart named `Mode Logic`.
- A MATLAB Function block named `Controller Force Law`.
- A Saturation block named `Force Saturation`.
- A Simulink-PS Converter named `Force Converter`.

The current saved model has been cleaned up into `Control` and `Plant`
subsystems, but the controller structure is the same.

## Validation

The project has two levels of automated checks.

`tests/testCraneValidation.m` verifies the design artifacts:

- Parameters load and are physically reasonable.
- The LQR gain is finite and has size `1-by-4`.
- The pump profile has enough samples and respects the force limit.
- Controller data is generated and saved.

`tests/testCraneLayoutBaseline.m` verifies that the current model still matches
the saved simulation baseline. Since the model now uses signal logging, the
test reads each signal from `simOut.logsout` by name and compares it with
`data/baselines/crane_sm_layout_baseline.mat`.

The handoff notes record the latest integrated behavior:

```text
Minimum wall-crossing clearance: 0.351 m
Crossing count: 1
Maximum contact force: 0 N
Tests: 4 passed, 0 failed
```

That is the right kind of evidence for this controller. The objective was not
to prove optimality. It was to show that the hybrid controller clears the wall,
does not hit the obstacle in the nominal run, and keeps the resulting behavior
stable enough for the catch phase.

## What I like about this design

The controller is intentionally split into pieces that match the physics:

- Pumping is about adding energy near the pendulum natural frequency.
- Transfer is about committing to the wall crossing at the right time.
- Post-clear control is about keeping the trolley from running away.
- LQR catch is about settling a small-angle state near the final target.

That split makes the Simulink model easier to explain. The Stateflow chart
answers, "What phase of the maneuver are we in?" The MATLAB Function block
answers, "Given that phase, what force should we apply?"

It also makes the project easier to tune. If the payload does not get high
enough, tune the pump. If it crosses too late, tune the transfer condition. If
it settles poorly, tune the LQR weights or scale factor.

## Project map

Here are the files that define the controller design:

| File | Role |
|---|---|
| `data/craneParameters.m` | Physical parameters, force limits, pump constants, LQR weights. |
| `scripts/designLQRCatchController.m` | Linear small-angle model and LQR gain computation. |
| `scripts/tunePumpManeuver.m` | Analytical nonlinear tuning loop for pump amplitude, duration, and phase. |
| `scripts/setupCraneController.m` | Generates `ctrl_*` variables and saves `craneControllerData.mat`. |
| `scripts/buildCraneSimscapeModel.m` | Shows how the Stateflow and MATLAB Function controller were generated. |
| `models/crane_sm.slx` | Current Simulink/Simscape implementation with `Control` and `Plant` subsystems. |
| `tests/testCraneValidation.m` | Unit checks for parameters, LQR gain, pump profile, and controller data. |
| `tests/testCraneLayoutBaseline.m` | Regression check against logged signal baseline data. |
| `HANDOFF.md` | Summary of the latest verified integrated behavior and remaining work. |

## One practical next step

The handoff notes say the final catch is good enough for the demo but not fully
polished. A natural next experiment is to add a small parameter sweep around
`p.lqrQ`, `p.lqrR`, and `p.lqrScale`, then score the final few seconds of
`xTrolley`, `theta`, and `omega`. That would keep the existing hybrid structure
and improve only the part of the maneuver that still needs refinement.
